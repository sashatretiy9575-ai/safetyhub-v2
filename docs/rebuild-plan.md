# План чистого восстановления SafetyHub

## Цель и границы

Этот план переносит рабочую локальную версию SafetyHub в **новый, чистый**
производственный контур. Старые Supabase, GitHub, Vercel и Cloudflare не
считаются источником рабочего кода и не используются как основа для
перезаписи. Их единственное назначение до удаления — инвентаризация,
зашифрованный backup и извлечение разрешённого контента.

Источник приложения — отдельная чистая копия локального проекта. В новый контур
переносятся только каталог курсов, статьи, проверенные PDF/миниатюры и
настройки, необходимые для работы сайта. Не переносятся прежние Auth-пользователи,
пароли, сессии, OTP-токены, профили, номера телефонов, аватары, попытки, оценки,
сертификаты, юридические согласия и аудит. Новый контур начинает историю
пользователей с нуля.

План не хранит секреты, адреса почты, пароли, ключи API, дампы, DNS-экспорты или
персональные данные. Они живут только в защищённых настройках соответствующего
провайдера или вне репозитория.

## Решения, зафиксированные до реализации

| Область | Решение |
| --- | --- |
| Сервер | Production работает на Supabase и Vercel; домашний компьютер и Docker никогда не являются сервером. |
| Авторизация | Только email → одноразовый цифровой код → сессия. Экранов пароля, регистрации с паролем, сброса/смены пароля и SMS нет. |
| Регистрация | Первый успешно подтверждённый email создаёт учётную запись. Затем человек заполняет профиль и отправляет запрос на доступ. |
| Доступ к обучению | Пока заявка не подтверждена администратором, недоступны PDF/материалы, вопросы, создание и продолжение теста, а также ответы API с учебным содержимым. Это проверяется сервером и RLS/RPC, а не только скрытием кнопки. |
| SLA | 24 часа — срок ожидания решения, а не автоматическое одобрение. По окончании таймера доступ не выдаётся: остаётся статус ожидания и показываются контакты администратора. |
| Телефон | Перед отправкой заявки пользователь вводит номер с выбором страны. Казахстан, Россия и Китай расположены первыми, затем полный список стран. Номер хранится нормализованно в E.164, без SMS-верификации. |
| Аватар | Приватный Storage, серверная повторная проверка изображения, канонический WebP, строго ограниченный доступ и короткоживущая ссылка на чтение. |
| Контент | Курсы используют три скрытых варианта по 10 вопросов, 4 варианта ответа, проходной балл 7, таймер 15 минут и не более 8 новых попыток на курс за день `Asia/Oral`. Ответы и идентификаторы вариантов не попадают в браузер. |
| Telegram | Не запускается в первой поставке. События одобрения проектируются так, чтобы позже подключить Telegram через outbox/webhook без изменения основной логики. |

## Фаза 0. Заморозка и инвентаризация старого контура

1. Зафиксировать точные идентификаторы старого проекта Supabase, Vercel-проекта,
   GitHub-репозитория, домена и фактического DNS-провайдера в закрытом release
   receipt вне репозитория.
2. Перевести старый контур в режим только чтение для команды: не применять к нему
   новые миграции, не публиковать из него контент и не менять DNS «на глаз».
3. Сверить все ресурсы старого Supabase: таблицы, миграции, RLS/RPC, Edge
   Functions, Auth-настройки, Storage buckets, размеры и количество объектов.
4. Зафиксировать, где реально обслуживается DNS. Если DNS остаётся в PS.KZ,
   Cloudflare используется только для Turnstile; перенос DNS-зоны не является
   необходимым условием новой выкладки. Почтовые MX/SPF/DKIM/DMARC и доменные
   verification-записи нельзя менять при обычном переносе сайта.
5. Сверить локальный каталог с hosted-контентом командой
   `npm run content:pull:linked -- --check`, когда доступны связанные учётные
   данные. При drift сначала получить и просмотреть контент, затем принимать
   решение, какая редакция является источником для миграции.

**Критерий завершения:** есть закрытая инвентаризация ресурсов и понятный список
контента для переноса; старый production ещё существует и не был удалён.

## Фаза 1. Backup до любого удаления

1. Создать свежий зашифрованный custom-format backup старой базы за пределами
   репозитория через `npm run db:backup:linked`. Он должен включать схемы,
   прикладные данные, Auth и Storage metadata, а ключ восстановления хранится
   отдельно от архива.
2. Выполнить проверку расшифровки, контрольные суммы и rehearsal восстановления
   только в одноразовом тестовом окружении. Production поверх production никогда
   не восстанавливается.
3. Отдельно создать зашифрованный manifest и byte-backup приватных аватаров.
   Это страховая копия, а не данные для автоматического импорта в новый проект.
4. Сохранить content receipt: курсы, статьи, опубликованные ревизии, PDF,
   миниатюры, SHA-256, количество страниц и контрольные числа каталога. В
   репозиторий не попадают персональные данные или plaintext dump.
5. Сверить backup: его проект ref, даты, размеры, количество строк и объектов,
   checksum. Если хотя бы одна проверка не пройдена, удаление старого контура
   блокируется.

**Критерий завершения:** имеется успешно расшифрованная и проверенная резервная
точка, а также отдельный проверенный receipt контента.

## Фаза 2. Чистая база Supabase и разбиение SQL

Создаётся новый Supabase project в выбранном ближайшем для аудитории регионе с
включёнными Data API и автоматическим RLS для новых таблиц. Его ref и ключи не
копируются в документацию или git. Новая база не связывается со старой и не
импортирует её пользователей.

Каждое изменение схемы оформляется только как новая forward-only миграция в
`supabase/migrations/`. Уже применённые файлы не редактируются, не переименовываются
и не удаляются. Supabase CLI ожидает плоский каталог миграций, поэтому "разбить по
файлам" означает небольшие упорядоченные `.sql`-файлы с понятными префиксами, а не
подкаталоги. Одна миграция отвечает за одну согласованную ответственность; если
операция требует атомарности, связанные команды остаются вместе.

Крупные исторические миграции, уже применённые в старом проекте, остаются
неизменяемым архивом: их нельзя безопасно «разрезать задним числом». Новый пустой
Supabase сначала воспроизводит проверенную схему из этой истории, а все изменения
восстановления — OTP, approval, телефон, закрытые PDF и прочее — добавляются только
новыми небольшими тематическими файлами. Отдельная полностью clean-room начальная
цепочка возможна позже лишь после независимого параллельного `db reset`/RLS-тестов;
она не станет непроверенной заменой работающей локальной версии во время cutover.

Начальный набор миграций должен быть разделён примерно так:

1. расширения, схемы `public`/`private`, общие helper-функции и базовые grants;
2. роли, профили, юридические согласия и минимальный audit;
3. заявки на доступ, статусы и audit решений администратора;
4. нормализованные телефоны, country metadata и индексы поиска/ограничений;
5. курсы, статьи, ревизии, presentation metadata и публичный read model;
6. приватные ключи тестов, три скрытых варианта, вопросы и ответы;
7. попытки, результаты, аттестации, сертификаты, дневные лимиты и timezone;
8. Storage buckets, policies, upload/finalize для PDF и аватаров;
9. learner RPC и RLS для материалов, тестов и результатов;
10. admin RPC, capability-проверки, notification outbox и эксплуатационные
    индексы/ограничения.

После каждой DB-правки обязательно обновляются
`lib/supabase/database.generated.ts`, `lib/supabase/types.ts`, SQL
contract/security-тесты и соответствующие документы. Миграции не вводятся вручную
через Supabase Dashboard.

**Критерий завершения:** чистая база поднимается с нуля одной последовательностью
миграций; `supabase db reset`, генерация/проверка типов и SQL-тесты проходят в
Docker-capable CI или во временном локальном окружении.

## Фаза 3. Passwordless email OTP

Новый пользовательский поток состоит из трёх коротких экранов:

1. человек вводит email и проходит Turnstile только после отправки формы;
2. сервер отправляет одноразовый цифровой код на почту и показывает нейтральное
   сообщение без раскрытия, существует ли такой email;
3. человек вводит код, сервер проверяет его и создаёт безопасную SSR-сессию.

Технические правила:

- используются отдельные серверные endpoints `otp/start` и `otp/verify` вокруг
  `signInWithOtp` и `verifyOtp`; клиент не получает service-role key;
- почтовый шаблон выдаёт `{{ .Token }}`, а не magic link; срок действия,
  повторная отправка и максимальное число проверок ограничены настройками Auth и
  server rate limit;
- на старте и проверке есть rate limit по IP, email hash и устройству, единые
  безопасные ошибки и audit без хранения кода;
- Turnstile проверяется на сервере с проверкой action и hostname; его токен
  одноразовый и не записывается в базу;
- UI и маршруты password login, password signup, reset password и change password
  удаляются либо перенаправляются на OTP. Старые invitation/password tickets не
  остаются рабочим путём;
- SMTP, Site URL и allowed redirect URL настраиваются в новом проекте перед
  production smoke; секреты задаются только в защищённых настройках провайдеров.

**Критерий завершения:** новый и существующий пользователь проходит путь
email → код → сессия; неверный, просроченный или повторно использованный код
отклоняется; в UI/API нет пути входа по паролю или SMS.

## Фаза 4. Профиль, заявка и подтверждение администратора

После первой OTP-сессии пользователь видит профиль и заполняет обязательные для
заявки данные. Телефон вводится через доступный keyboard-first country picker:

- первые элементы: Казахстан (`KZ`), Россия (`RU`), Китай (`CN`);
- далее полный стабильный список ISO 3166-1 стран с флагом, названием и calling
  code; поиск не меняет фактическую страну без выбора;
- база хранит ISO country code отдельно от нормализованного `phone_e164`;
- сервер повторно валидирует номер библиотекой для телефонной нумерации. Поле
  помечено как контактное и **не считается SMS-подтверждённым**.

Заявка имеет серверно управляемый lifecycle: `draft` → `pending` → `approved` или
`rejected`. При отправке фиксируются `submitted_at` и
`approval_due_at = submitted_at + 24 hours`. Таймер в кабинете строится по
`approval_due_at`, полученному с сервера. После нуля он меняется на понятное
сообщение, но не переводит пользователя в `approved`, не удаляет заявку и не
выдаёт доступ автоматически.

У администратора появляется защищённая очередь заявок: данные профиля, время
подачи, дедлайн, решение, причина отказа при необходимости и неизменяемая запись
кто/когда принял решение. Решение выполняется одним admin RPC с capability-check,
optimistic/idempotency защитой и audit event. Только после commit успешного
`approved` пользователь может читать учебные материалы.

В pending и overdue состоянии пользователь всегда видит управляемые настройками
контакты администратора: безопасную кнопку звонка (`tel:`) и WhatsApp-ссылку.
Номер не хардкодится во фронтенде, проходит валидацию и доступен только там, где
нужен. При отказе доступ также не открывается, а интерфейс сообщает следующий
допустимый шаг без утечки внутренних комментариев администратора.

Аватар восстанавливается как отдельный надёжный поток: клиент предварительно
уменьшает изображение, сервер повторно декодирует, ограничивает размеры/тип/вес,
убирает metadata, сохраняет канонический WebP и вычисляет hash. Bucket остаётся
приватным; пользователь получает только собственный аватар, администратор — лишь
обоснованный доступ, а чтение идёт через short-lived signed URL или серверный
маршрут. Ошибка загрузки не должна ломать сохранение других полей профиля.

**Критерий завершения:** в тестовом аккаунте нельзя открыть материалы/тест до
ручного одобрения; countdown корректен на границе 24 часов; admin approve сразу
открывает доступ, reject — нет; телефон и аватар сохраняются безопасно.

## Фаза 5. Серверный gate учебного контента

Публичными могут оставаться только описания и маркетинговый каталог. Следующие
операции обязательно повторно проверяют server-side состояние `approved`:

- выдача PDF/презентации и signed download URL;
- получение learner payload с вопросами;
- создание или возобновление попытки;
- сохранение ответа, завершение и оценивание попытки;
- любые RPC, которые раскрывают защищённый учебный контент.

PDF, предназначенные только для одобренных участников, не должны быть доступны
по постоянному публичному URL. Для них применяется приватный bucket или
серверный download endpoint, выдающий короткоживущий URL после проверки
одобрения. Проверка присутствует в RLS и RPC, поэтому прямой REST-вызов,
подмена маршрута или скрытие кнопки в браузере не обходят правило.

Участник никогда не получает `variant_id`, номер варианта, правильный ответ,
answer-key table или метаданные неопубликованной презентации. Вопросы выдаются
только для уже назначенной попытки. Создание новой попытки серверно проверяет
одобрение, лимит 8 в календарный день `Asia/Oral`, срок 15 минут и назначает один
из трёх скрытых вариантов в транзакции.

**Критерий завершения:** неавторизованный, pending и rejected пользователь не
получают PDF, вопросы или ключи даже при прямом запросе; approved пользователь
получает только свой разрешённый learner payload.

## Фаза 6. Миграция проверенного контента

1. Проверить локальные snapshot/исходные материалы, hashes и PDF визуально.
2. В новой базе применить схему и создать пустые buckets/policies скриптом или
   миграциями; не вставлять контент вручную через Dashboard SQL.
3. Импортировать опубликованные курсы, статьи, presentation metadata и assets
   контролируемым административным flow. Каждый PDF получает новый неизменяемый
   content-addressed path; опубликованный объект никогда не перезаписывается.
4. Для каждого курса сверить 3 варианта × 10 вопросов × 4 ответа, один правильный
   ответ, проходной балл 7 и длительность 15 минут. Затем опубликовать только
   подготовленную и проверенную ревизию.
5. Выполнить `npm run content:pull:linked`, просмотреть детерминированный diff,
   затем `npm run content:parity:check` и snapshot validation. Snapshot содержит
   только контент, никогда не пользователей или учебную историю.

**Критерий завершения:** новый каталог совпадает с утверждённым content receipt,
PDF открываются только после approval, а локальный snapshot детерминированно
повторяет hosted-контент.

## Фаза 7. GitHub, Vercel, Cloudflare и домен

### GitHub

1. Создать **новый приватный** репозиторий из чистого локального root commit.
2. Проверить `.gitignore`: никаких `.env*`, backup, recovery key, `.vercel`,
   Supabase temporary link, пользовательских выгрузок или токенов.
3. Включить CI на поддерживаемом Node 24: application gate, disposable Supabase
   database gate, SQL/RLS tests и release E2E. Настроить branch protection и
   обязательные checks до production.
4. Старый GitHub-репозиторий остаётся архивом до завершённого cutover; затем
   удаляется только после подтверждённого smoke и rollback window.

### Vercel

1. Создать новый Vercel project, связать только с новым приватным репозиторием и
   настроить Preview/Production variables в панели Vercel.
2. Сначала проверить Preview на отдельном URL: OTP, profile, approval, course
   gate, uploads, admin queue и error paths.
3. После production smoke подключить canonical domain к новому Ready deployment;
   `www` должен постоянно перенаправляться на apex. Старый deployment остаётся
   быстрым rollback на согласованное окно.

### Cloudflare и DNS

1. Создать/перепривязать только новый Turnstile site и его server secret для
   production hostname. Старый ключ отозвать после проверки нового.
2. До любой DNS-операции экспортировать и сверить записи. Если authoritative DNS
   не в Cloudflare, не переносить туда зону без отдельного решения.
3. При обновлении Vercel-записей менять только записи сайта. Сохранить MX, SPF,
   DKIM, DMARC, почтовые и сторонние verification records.

**Критерий завершения:** production использует только новые Supabase и Vercel
ресурсы; домен имеет валидный TLS и canonical redirect; почта и DNS не повреждены.

## Фаза 8. Верификация, наблюдаемость и cutover

Ниже — обязательный release gate. Локальный Docker допустим только как временный
инструмент для воспроизводимого database test; он не запускает сайт и не нужен
после проверки. Если локальная виртуализация недоступна, тот же Docker-capable
database gate выполняется в CI. Никакой сервис не остаётся зависимым от
включённого персонального компьютера.

1. Запустить узкие тесты во время изменений, затем `npm run verify`.
2. На чистой базе/CI выполнить `supabase db reset`, генерацию и проверку типов,
   `npm run check:db-types`, `npm run test:db`, seed и authenticated E2E.
3. Проверить OTP: resend/rate limit, неверный/просроченный/повторный код,
   существующий и новый email, отсутствие password/SMS flow.
4. Проверить роли: public, anonymous, pending, overdue, rejected, approved и
   admin. Для каждой роли выполнить UI- и прямые API/RPC/Storage-запросы.
5. Проверить телефон (KZ/RU/CN и страна из полного списка), keyboard/accessibility,
   нормализацию E.164, приватность номера и неработающий bypass через форму.
6. Проверить аватар: допустимые/недопустимые MIME, лимиты, удаление metadata,
   failure recovery, RLS и отсутствие публичного object URL.
7. Проверить все курсы: PDF, вопросы, возобновление, таймер, лимит, оценивание,
   сертификат и отсутствие answer key в HTML/JSON/logs.
8. Проверить production: HTTP/TLS/canonical, SEO, Vercel и Supabase errors/latency,
   SMTP delivery и Turnstile server validation. Зафиксировать обезличенный
   release receipt.

**Критерий завершения:** все обязательные команды и smoke проходят; доступ к
production домену даёт именно новый контур; есть рабочий rollback на прежний Ready
deployment и проверенный backup старого контура.

## Фаза 9. Удаление старых ресурсов — только последней операцией

Удаление выполняется только после успешного production smoke, проверки backup,
сверки контента, подтверждённого нового администраторского входа и согласованного
rollback window (рекомендуется не меньше 7 дней). Последовательность:

1. Сделать финальный read-only count check и сохранить его вместе с backup receipt.
2. Убедиться, что новый Vercel production не обращается к старому Supabase, а
   новый домен/SMTP/Turnstile используют только новые настройки.
3. Удалить старых пользователей только в старом Supabase после сохранённого
   backup; в новый проект их не копировать.
4. Удалить старые Supabase project, GitHub repository, Vercel project и
   неиспользуемые Cloudflare/Turnstile resources по их точным идентификаторам.
   DNS-зону и почтовые записи не удалять, если они продолжают обслуживать домен.
5. После каждого удаления проверить, что production домен, OTP, загрузка аватара,
   admin approval и курс всё ещё работают. Зафиксировать результат без секретов.

Если smoke или контрольная сверка не проходят, удаление отменяется, а исправление
делается forward migration или rollback приложения — не ручным восстановлением
отдельных production-строк и не destructive down migration.

## Telegram — отдельная последующая поставка

После стабилизации основного потока можно подключить Telegram-уведомление о
новой заявке. Для этого используется запись события в `notification_outbox` после
успешной транзакции заявки, идемпотентный серверный worker, retry/backoff,
минимальный payload без лишних персональных данных и audit результата доставки.
Токен бота, chat ID, формат уведомлений и список получателей настраиваются только
после отдельного решения владельца. Сбой Telegram никогда не должен отменять
заявку, approval или доступ к сайту.

## Итоговые критерии готовности

- Новая инфраструктура независима от старой, а код и migrations находятся в новом
  приватном GitHub-репозитории без секретов.
- Пользователь входит только одноразовым email-кодом; пароль и SMS отсутствуют.
- До ручного одобрения администратором 24-часовой countdown не даёт доступ к
  материалам, PDF или тесту; после одобрения доступ появляется на серверном уровне.
- В профиле работают безопасный аватар и телефон с country picker (KZ/RU/CN
  первыми и всеми остальными странами).
- Каталог, тесты, PDF, RLS и ответные ключи соответствуют учебному контракту и
  не раскрывают закрытые данные в браузере.
- Старые облачные ресурсы удаляются только после подтверждённого backup, полного
  smoke и окна rollback; персональный компьютер не используется как production
  сервер.
